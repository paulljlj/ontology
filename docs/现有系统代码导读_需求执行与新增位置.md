## 先记住这几个结论

- 当前网页显示的是数据分析工作台，实际入口为 `ReportWorkbench`。
- 原来的 `Feature → Spec → Plan → Task` 软件需求链仍在后端，但当前网页的报表执行不走这条链。
- 新报表链是“关键词和时间规则解析 → 从目录选择步骤 → 任务入库 → Python 顺序执行 → 生成报告”。
- 实际调度依据是 `task_key → handlers → Python 函数`。`skill_spec` 当前主要记录技能说明、能力标签和依赖，不是生成的新程序。
- 真正的 OWL 模型和 Pellet 推理能力存在，但报表执行器没有调用它们来生成任务计划。前端运行图也是按执行记录构造的展示图。
- 本次只读核实应用代码，新增的是这份导读，没有修改业务实现，也没有运行会写数据库、发审批或同步图谱的流程。

## 1 当前网页怎样完成一次用户需求

以“分析最近三个月各区域的销售额和回款”为例。

```text
用户在 ReportWorkbench 输入需求
  ↓ submit()
前端 api.createReportRun() 发送 POST /api/report-runs
  ↓
report_routes.create_report_run()
  ├─ create_workflow_run()
  │    ├─ compile_result_contract()：提取指标、维度、时间和分析意图
  │    ├─ build_task_plan()：从已有任务目录选步骤
  │    └─ 保存运行记录与每一步任务
  └─ BackgroundTasks 启动 execute_workflow_run(run_id)
       ├─ 按 order_index 读取任务
       ├─ 根据 task_key 从 handlers 找到处理函数
       ├─ 处理函数读表、清洗、统计，并通过 context 传递中间结果
       └─ 生成报告、保存证据和文件记录
  ↓
前端轮询运行状态，展示进度、关系图、结果和下载入口
```

### 关键片段一 需求解析并不是大模型自由规划

位置：[指标与维度提取](J:/environment/vs-code/shiyanshi/ontology/backend/app/application/report_workflow.py:284)。

当前通过 `_mentioned()` 匹配预设词表，通过 `_extract_time_scope()` 识别时间范围。例如，命中“区域”就产生维度信息，命中“趋势”就增加趋势分析意图。原始需求也保存在结果合同中。

得到的 `result_contract` 是“本次要分析什么、交付什么”的字典，不是原来软件需求链中的 `Spec` 本体实例。

### 关键片段二 根据分析意图选已有任务

位置：[任务选择分支](J:/environment/vs-code/shiyanshi/ontology/backend/app/application/report_workflow.py:365)。以下为源码节选：

```python
if "dimension_comparison" in intents:
```

这不是对所有 Task 做语义搜索，而是按条件选择预定义步骤。最终 `task_plan` 是步骤列表，并不是创建了原来的 `Plan` 本体对象。

步骤定义来自 [TASK_BLUEPRINTS](J:/environment/vs-code/shiyanshi/ontology/backend/app/application/report_workflow.py:59) 和 [TASK_CATALOG](J:/environment/vs-code/shiyanshi/ontology/backend/app/application/report_workflow.py:135)。

### 关键片段三 每一步记录标识 顺序和技能配置

位置：[创建 ExecutionTaskORM](J:/environment/vs-code/shiyanshi/ontology/backend/app/application/report_workflow.py:476)。以下为源码节选，省略了其他字段：

```python
task_key=key,
order_index=index,
skill_spec={
    "name": skill_name,
    "generated_for_run": True,
    "required_capabilities": capabilities,
    "mcp_bindings": bindings,
    "permission_policy": "workspace-scoped",
    "depends_on": [previous_key] if previous_key else [],
    "ontology_rule": reasoning["rule"],
},
```

- `task_key`：步骤标识，执行器实际用它查找函数。
- `order_index`：实际读取和执行的顺序。
- `skill_spec`：技能说明与配置记录；`generated_for_run=True` 不代表已经生成新源码。
- `depends_on`、`mcp_bindings` 等是声明。目前没有按这些字段进行通用 DAG 调度或外部 MCP 分发。

### 关键片段四 执行器怎样找到函数

位置：[handlers 映射表](J:/environment/vs-code/shiyanshi/ontology/backend/app/application/report_workflow.py:570) 和 [实际调用](J:/environment/vs-code/shiyanshi/ontology/backend/app/application/report_workflow.py:597)。以下是保留核心逻辑的简化示意：

```python
handlers = {
    "clean_merge": _clean_step,
    "calculate_summary": _summary_step,
    "compare_dimensions": _dimension_step,
    "generate_report": _report_step,
}

for planned_task in planned_tasks:
    key = planned_task["key"]
    evidence, outputs = handlers[key](run_id, context)
```

一个 `task_key` 当前映射到一个步骤处理函数。这个处理函数内部可以继续调用多个底层函数。`context` 是本次运行共享的数据字典，后续步骤从中读取清洗后的行、统计结果等中间数据。

## 3 本体 推理机和前端图谱分别在哪里

### 本体定义是真实存在的

- [ontology.py 的类定义](J:/environment/vs-code/shiyanshi/ontology/backend/app/domain/ontology.py:37)：规定系统认识哪些对象。
- [字段约束](J:/environment/vs-code/shiyanshi/ontology/backend/app/domain/ontology.py:368)：规定哪些字段必填、允许什么类型和取值。
- [关系定义](J:/environment/vs-code/shiyanshi/ontology/backend/app/domain/ontology.py:480)：规定哪些类型的对象可以建立哪种关系。
- [reasoner 的实例检查](J:/environment/vs-code/shiyanshi/ontology/backend/app/domain/reasoner.py:67) 与 [关系检查](J:/environment/vs-code/shiyanshi/ontology/backend/app/domain/reasoner.py:114)：常规创建对象和关系时使用的快速检查。

### 真正调用 Pellet 的代码

- [validate_with_pellet](J:/environment/vs-code/shiyanshi/ontology/backend/app/domain/reasoner.py:231)：提供一致性校验能力；当前应用主流程没有调用它。
- [compute_inferred_edges](J:/environment/vs-code/shiyanshi/ontology/backend/app/domain/reasoner.py:298)：调用 Pellet，计算传递性等限定范围内的推导边。
- [POST /reasoning/materialize](J:/environment/vs-code/shiyanshi/ontology/backend/app/api/routes.py:152)：显式触发推导，并把推导关系写入 Neo4j。

常规创建对象时按 OWL schema 做快速检查，不等于每一次创建都启动 Pellet。当前应用中未见 SWRL `Imp` 或 `set_as_rule` 定义。

### 报表页右侧运行图是前端拼出来的

[buildRuntimeGraph](J:/environment/vs-code/shiyanshi/ontology/frontend/src/components/ReportWorkbench.tsx:539) 根据 `run`、`tasks`、`result_contract` 构造节点和边，再交给 `Topology` 绘制。

所以图中出现 `Plan`、`SkillDefinition`、虚线或 `inferred=true`，不代表这些关系已由 Pellet 推导或已作为本体实例落库。`Dimension`、`AnalysisIntent`、`TimeScope` 等也有前端展示用途，不能直接当成已定义的 OWL 类。

报表后端的 [ONTOLOGY_REASONING](J:/environment/vs-code/shiyanshi/ontology/backend/app/application/report_workflow.py:190) 与 [ontology_reasoning_for](J:/environment/vs-code/shiyanshi/ontology/backend/app/application/report_workflow.py:411) 是解释模板与文本组织逻辑，不是推理机自动生成任务的证据。

## 7 对外介绍时避免说错的地方

| 容易说过头的表述 | 按当前代码应该怎样说 |
| --- | --- |
| 自动制造任意新 Skill | 根据需求组合预定义步骤，生成本次技能配置；函数实现仍由开发者提供 |
| skill_spec 决定所有工具调用 | 当前由 `task_key` 查 `handlers`；skill_spec 主要是声明与记录 |
| 报表任务全部由 OWL/Pellet 推出来 | 当前按关键词、分析意图和任务目录编排；报表链没有调用 Pellet |
| 页面右图都是数据库中的推理结果 | 报表页运行图由浏览器根据运行记录构造，含展示用节点和关系 |
| 每一步都实际调用了 MCP | 报表内是本地函数调用；MCP Server 提供对外入口，CLI Agent 另有真实 MCP 调用 |
| 页面已经自动接上外部业务数据 | 当前页面默认内置演示表；MCP 报表入口可传工作区文件，但没有通用外部数据发现调度 |
| 异常检测已支持卫星根因分析 | 当前异常步骤是缺失与低回款率等演示条件；卫星数据、关系和候选比较尚需新增 |
| 文件验证通过说明原因判断正确 | 当前主要检查交付文件与非空结果，没有卫星 Top 1/Top 3 等实测评价 |

只想抓住主线时，先读 `report_routes.py`，再依次看 `report_workflow.py` 中的 `compile_result_contract`、`build_task_plan`、`create_workflow_run`、`execute_workflow_run`。理解这条执行链后，再看本体、前端图谱与其他集成。
