# 卫星分析首版：技术方案与两人分工

> 历史方案存档，正文保留原貌，不代表当前完成状态。2026-10-19的实际分工已经调整：我们负责备选路径、本体、任务执行、真实MCP、API、前端与下载；同学负责诊断五部分，尚待交付。路径和系统首版已实现，旧MVP已推送。本分支权威进度、接口和分工请先读[HANDOFF.md](../HANDOFF.md)，不要沿用下文旧表。

## 一、首版要交付什么

用户选择一个文件案例和分析时段，系统自动执行分析，输出六部分报告：异常概况、根因候选与原因、轻微持续下降、备选通信路径、影响与正常对照、待补证据。

复用已有的需求入口、任务计划、执行记录、进度展示和报告下载。新增卫星领域定义与真正执行分析的Python函数。先跑通文件数据，不接真实设备控制，不先训练复杂模型。

这是后续实施方案。本文所列新模块、接口和能力均为拟新增，尚未实现。

## 二、完整技术流程

```text
选择案例、时段，输入分析要求
            ↓
生成 task_plan，确定本次要执行的步骤
            ↓
读取文件并校验，按证据截止时间截取数据
            ↓
识别明显异常和未超重大阈值的持续下降
            ↓
按本体定义的关系构建当时网络快照，找共同依赖与正常对照
            ↓
比较指标、负载、告警，解释和排序候选原因
            ↓
生成备选路径，验算同时改路后的容量和业务约束
            ↓
形成结构化报告，展示依据、限制并支持下载
```

### 本体、任务和Python各负责什么

- 本体：定义“是什么、依赖谁”。新增或复用卫星、地面站、通信链路、路由、网络业务、指标观测、告警等对象及关系。带时间的路由数据在Python侧按生效区间构建快照，避免混用不同时刻的路径。
- task_plan：安排步骤顺序。每步以task_key标识，skill_spec描述所需处理器、参数及输入输出。
- 执行器：通过允许调用的处理器注册表找到真实函数，并保存输出、证据和执行状态。需要让新增流程实际使用这套绑定，不能只生成skill_spec文字。
- Python分析函数：计算下降幅度、持续时间、候选证据及备选路径可行性。
- 大模型：首版只辅助解析要求、组织报告文字。指标与结论依据来自函数结果，不由大模型编造。

首版技能封装的是已经写好的分析能力，不要求AI临时生成任意可执行代码，也不需要把每个函数都单独搭成MCP Server。本地函数先跑通，后续有远程服务需求再包装为MCP工具。

## 三、两人分工

A负责“把能力接进系统并展示”，B负责“把数据分析计算做出来”。

| 负责人 | 具体工作 | 交付物 |
| --- | --- | --- |
| A：本体与系统集成 | 定义领域类和关系；约定输入输出；新增卫星任务计划和处理器绑定；接API、执行进度、报告展示与下载 | 系统里能选择案例、点击运行、看到每步状态和六部分报告 |
| B：分析与路径能力 | 读取和校验CSV；实现明显/轻微异常检测；按关系查共同依赖和对照；比较原因；生成并验算备选路径 | 能脱离前端独立运行的Python分析函数、结构化结果和测试 |

A定义“哪些对象之间允许有什么关系”，B按这套定义导入实例并查询、计算。前端只展示后端结论，不能再自己计算一套异常规则。

## 四、B的分析能力具体怎么做

| 能力 | 首版方法 | 要输出什么 |
| --- | --- | --- |
| 明显异常 | 按演示规则比较正常基线、下降幅度和连续有效采样点 | 业务ID、时段、下降百分点、持续时间、证据ID |
| 轻微持续下降 | 下降未超过重大阈值，但满足持续时间并伴随高负载或设备错误 | 关注对象、支持信号、尚未达到的重大条件；不输出未经校准的故障概率 |
| 共同依赖 | 查询异常业务当时经过的节点和链路，保留多个候选 | 卫星、站点、链路候选及覆盖业务；不直接宣布共同对象就是故障 |
| 原因比较 | 分组对照，加可解释条件判断 | 候选对象、可能机制、支持证据、反对证据、缺失证据和排查顺序 |
| 备选路径 | 先枚举少量有效路径，再放入全部待迁移流量验算 | 路径、可行/不可行、原因、预计负载与时延；没有可行方案时明确返回 |

原因比较先覆盖四种机制：

- 过载：到达流量超过有效转发容量，并有丢弃或队列证据。不能只数经过多少条路由。
- 地面站侧：同站不同中继的业务也下降，并有站侧电压或设备告警；单换中继未必能解决。
- 链路侧：经过同一链路的业务下降，而绕开该链路的可比业务正常，同时链路质量有变化。
- 辐射相关设备错误：环境计数与存储错误、重启等证据共同出现。仅环境计数高不够，结论先写“疑似相关”。

这些是首版可检验的诊断条件，不是完整因果证明。暂不要求贝叶斯网络、PCMCI+或分类模型。

## 五、第一天先共同约定接口

先写satellite_schemas.py，再各自开发。至少统一以下内容：

| 约定 | 内容 |
| --- | --- |
| 输入 | case_id、分析开始/结束时间、证据截止时间as_of、规则版本 |
| 数据口径 | ID与CSV一致；时间带时区；可用度为0至100；下降用“百分点”；流量用Mbps；空值不等于0 |
| 分析上下文 | 文件适配器提供业务、当时有效路由、资源状态及样本；业务分析函数不自行读取其他案例或未来证据 |
| 报告输出 | overview、causes、watch_items、route_options、impact、limitations，另附统一evidence列表 |
| 原因状态 | 区分候选、证据支持、证据不足；没有独立确认时不写“已确认故障” |
| 证据引用 | 关联sample_id或event_id，能定位CSV、对象和时间；规则及数据版本一并保存 |
| 改路结果 | 保留源和允许的出口，返回可行性、限制及模拟指标；不表示已经切换设备 |

B的函数采用明确的“输入数据→结构化输出”形式，逐步对应读取、检测、候选、比较和路径处理器。A先用相同格式的固定示例结果开发页面，联调时换为真实函数，不用等B全部做完。

若skill_spec缺处理器、数据不完整或某步失败，执行器记录失败/缺证状态；不能自动用生成文字补成成功。

## 六、分三轮交付，不要一次铺开

### 第一轮：一个案例完整跑通

A先保留当前系统版本并搭卫星流程和页面。B先完成CASE-001的数据读取、明显/轻微异常和过载证据。共同验收：页面上的数字确实来自CSV，能看到SAT-20候选与SAT-24关注对象，结论能点开证据。

### 第二轮：补齐原因与改路

B补地面站、链路、辐射相关和备选路径验算；A接入完整报告、网络关系展示与下载。共同验收：10条业务一起迁移后仍满足容量和业务约束，且没有拖坏未迁移业务；明确保留原本未解决的风险。

### 第三轮：专门检查系统会不会乱下结论

共同跑正常切换、环境计数高但业务正常、遥测缺失和无可行备选路径案例。验收重点：计划内短暂波动不当成持续故障，数据缺失不填0，不读取未来恢复记录，没有可行路径不强行推荐。

诊断模块不得读取evaluation目录。验收脚本可以读取独立答案进行核对。八个设计案例用于验证首版功能，不足以证明真实卫星诊断准确率。

## 七、版本和部署由A统一负责

先按原要求将当前已有系统保存至dataanalyseorigin分支，保护现有未提交代码，并单独保留配置和运行数据。两人用各自开发分支或副本工作，不同时修改同一个运行目录。

卫星版先使用隔离数据库、配置和端口验证，旧经营分析流程仍要能运行。验证通过再接替当前本地入口；不要先删除或整体覆盖ontology目录。此方案不代表已经执行Git推送或部署切换。
