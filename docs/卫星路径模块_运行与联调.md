# 卫星路径模块：运行与联调

> 当前交接分支为`fengongdemo1`，先读仓库根[HANDOFF.md](../HANDOFF.md)。2026-10-22已合并同学诊断模块，诊断部分见[同学诊断模块整合说明](同学诊断模块_整合说明.md)。下文保留2026-10-19路径模块的手工运行记录和绝对路径示例；新账号/新电脑不能复制旧绝对路径。

## 1. 这次完成的范围

职责仍分开但已经联调：同学代码负责数据诊断，我们负责路径建议、本体约束、任务执行、MCP、页面和下载。

现在可以独立跑通：

`选案例 → 读取时点数据 → 本体校验 → 自动诊断候选与证据 → 联合计算备选路径 → 六部分报告 → 文件校验与下载`

默认自动运行已接入的同学诊断函数；也继续支持粘贴外部诊断JSON或关闭诊断后手动测试待避对象。本地图模式不冒充MCP，Neo4j MCP模式需单独完成实机配置与验收。

当前是按已注册能力生成的场景化小计划，不是任意自然语言自动生成Python代码。每一步的`skill_spec.processor`实际映射到处理器；`depends_on`控制依赖；处理器再调用路径函数或MCP。`requirement`保留用户要求，但当前不会改变既定算法或自由创建新工具。

## 3. 两个真实MCP分别做什么

| Server | 版本 | 实际工具 | 作用与权限 |
| --- | --- | --- | --- |
| mcp-server-motherduck（使用本地DuckDB，不接云） | 1.0.8 | execute_query | 查询11个observed表；数据库只读，禁止外部文件访问与扩展加载 |
| 官方Filesystem MCP | 2.0.0 | write_file、get_file_info | 写入和核对本次JSON/HTML；允许目录仅为backend/report_artifacts/satellite |

系统真实执行`initialize → list_tools → call_tool`，校验工具参数，保留服务器、版本、参数摘要、耗时、结果摘要和失败。正常运行当前有14次工具调用。MCP失败会使运行失败，不会暗中切到文件模式。

路径搜索本身是卫星专用Python能力；MCP承担通用数据查询和产物能力，不把普通Python函数冒充开源MCP。配置状态只代表“已配置”，成功调用要看本次执行日志。

已准备好的本机配置在`.satellite-runtime/mcp-servers.local.json`，不提交绝对路径到Git。没有该配置时会明确进入文件模式，不宣称调用了MCP。

开源来源：[MotherDuck MCP](https://github.com/motherduckdb/mcp-server-motherduck)、[官方Filesystem MCP](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem)。

以下命令从仓库根目录执行；当前电脑已经装好，无需重复安装：


`requirements-satellite-mcp.txt`列出主要服务版本，`backend/mcp/python-runtime.lock`记录本次Windows/Python3.12实测完整依赖；其他平台应重新验证。准备脚本只导入`observed`11表，并保存CSV哈希；数据变动后要重新准备。`evaluation`、答案文件及manifest不进入运行数据查询。

无凭据、无外网访问也能执行分析。首次安装依赖需要联网。无配置时可以仅用文件模式运行路径CLI。


前两条完整流程示例中的`python`应使用装有原项目后端依赖的解释器，而不是只装MCP服务的隔离解释器。当前电脑为`J:\environment\Anaconda\envs\agent_env\python.exe`。

API：POST `/api/satellite/runs`，例如：

```json
{"case_id":"CASE-001","avoid_objects":["SAT-20"],"max_utilization_pct":85,"max_latency_ms":150,"max_options":3}
```

## 6. 同学最后对接什么

先把这两个文件发给她：

- `docs/satellite-diagnosis.schema.json`：正式JSON Schema，由Pydantic模型导出。
- `docs/satellite-diagnosis.example.json`：字段和证据引用样例，标记为development_fixture。

她的`.py`可以独立开发，不需要安装我们的前端、OWL或运行数据库。交付时用`analyze(data_dir, case_id, analysis_start, analysis_end, as_of) -> dict`这类函数返回上述结构，CLI打印同一JSON。算法和函数命名由她决定，JSON接口保持一致。

必须有：case_id、analysis_start、analysis_end、as_of、source，以及overview、causes、watch_items、impact、conclusions、missing_evidence、evidence。时间必须带时区；analysis_end为不含终点的时段边界。

每条证据填写`evidence_id/object_id/timestamp/available_at/source_file/record_id`，对应真实观测行。候选使用supporting_evidence_ids、contradicting_evidence_ids引用它。原因状态区分candidate、supported、insufficient_evidence；supported仅代表有支持证据，仍不是独立确认的真实根因或概率。

分析只能使用`timestamp`与`available_at`均符合截止条件的数据；本次快照默认取分析窗最后一个完整采样点。不能用后续恢复记录解释“当时已知”的原因。`evaluation`只在她独立测试时核对，不能作为分析输入。

初次联调直接把JSON粘贴到页面的“外部诊断”输入框，不用先开新HTTP服务。后续可以在已注册诊断处理器内调用她的函数，或把其封装为团队自己的卫星诊断MCP Server；后者须标明自研，不称为网上现成Server。

## 7. 路径建议究竟检查什么

- 有向路径连续，保留业务源和允许地面站出口；检查本时段接触窗口。
- 避开指定节点/链路，不把反向链路当作正向可用。
- 所有待迁移业务一起计算预留流量；共享节点和链路都不得超过85%可配置上限。
- 估算传播、处理与排队时延；同时检查未迁移但共享资源的业务，不能只优化一条业务而拖垮其他业务。
- 扣除上游丢流时采用保守背景负载估计；关键流量/遥测缺失时不给“确定可行”结论。

目前是有限候选路径搜索加联合回溯，不保证全局最优。对SAT-20进行人工待避时，CASE-001可找到经SAT-21的方案，但其他既有瓶颈可能仍在。地面站没有允许替代出口时，即使能找到图上的路，也应返回无可行方案。数据缺失则返回insufficient_data。

85%和150ms是演示参数，不是甲方标准。输出是模型估计，不是切换后的真实吞吐量或可用度。当前不做真实设备切换，不声称验证全部SLA，也不负责确认“宇宙辐射导致故障”。

| 计划、skill_spec、处理器映射与报告 | backend/app/application/satellite_workflow.py |

| 页面、六部分报告与执行证据 | frontend/src/components/SatelliteWorkbench.tsx |

本体中的Satellite/GroundStation/CommunicationLink统一网络对象类型，Route与NetworkService表示通信路径与业务；MetricObservation/AlarmEvent放观测与告警；NetworkSnapshot限定时点；RouteProposal表示路径建议。关系如LINK_SOURCE、LINK_TARGET、ROUTE_USES_NODE、SERVICE_USES_ROUTE、OBSERVES_ENTITY等。

本流程实际调用OWL声明派生的类型/关系校验，再由Python检查容量和时延；不是让Pellet计算最短路或自动证明因果。`engineering.owl`已由Python本体声明同步导出，既有本体规则保留。重新修改本体声明后可在backend执行`python -c "from app.domain.ontology import export_ontology; export_ontology()"`更新快照。
